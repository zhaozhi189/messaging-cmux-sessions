# 多会话协作模式(进阶)

`cmux send` 适合"随手一戳"。任何你需要**确知落地**的事——任务交接、评审结论、接口交接、跨会话决策——都要升级到本文的模式。

**根本问题:** `cmux send` 是往脆弱 TUI 里注入键盘,单向、无投递保证、无回执。验证 `❯` 空了只证明*提交*,不证明*理解或完成*。

**核心原则:把文件系统当通道,`cmux send` 只当门铃。**

> 下文的 `$S` 即 SKILL.md 里定死的脚本目录:`S=~/.claude/skills/messaging-cmux-sessions/scripts`。

---

## 模式一:文件信箱 + ack(正确性重要时)

消息和回执都是文件;cmux 只负责叫醒对方。

```
cmux-bus/<session>/inbox/<msgid>.md   # 发给 <session> 的一条消息
cmux-bus/<session>/ack/<msgid>.md     # <session> 的回执:已处理 <msgid> + 结果摘要
```

1. **发送方**把完整载荷写到 `cmux-bus/<peer>/inbox/<id>.md`,frontmatter 带 `id / from / to / need_ack / subject`。铁打的:不 wrap、不用 shell 转义、不丢 `\r`,而且自带归档。
2. **发送方**按门铃——一条**短**行(不会 wrap → 干净提交):
   ```bash
   $S/send.sh <peer> 'inbox 有新消息 <id>,请读取并 ack'
   ```
   然后按铁律验证退出码。
3. **接收方**读 inbox 文件 → 干活 → 写回执 `cmux-bus/<sender>/ack/<id>.md`,带结果摘要。
4. **发送方确定性地闭环**:轮询 **ack 文件是否存在**,而不是盯对方屏幕瞎猜。超时无 ack → 再按一次门铃 / 升级给用户。

**为什么胜过 send + verify:** 正确性押在文件系统(可靠)上,不押在 TUI 按键(易碎)上。ack 证明*对方确实处理了*,这是 read-screen 永远给不了的。而且门铃即便失败,一个在自己 tick 里轮询 `inbox/` 的对方仍会捡到——**两条独立投递路径,没有单点丢失**。

### 整套协议太重时的轻量变体

- **拿可观察副作用当 ack**:别问"你收到了吗",盯它被要求产出的*效果*——一个新 commit、一个写出的文件、一行状态。宁可要一个可检查的副作用,也不要一句口头 "done"。
- **只轮询(无门铃)**:若各方都在跑循环,干脆丢掉 `cmux send`,每个会话每 tick 扫自己的 `inbox/`。慢一些,但零依赖键盘注入。
- **共享 append-only 日志**(`cmux-bus/chat.jsonl`):所有会话往一个文件追加 `{id, from, to, ts, body}` 及其 ack,各自轮询 `to == me`。单一事实源,完全可审计。

**经验法则:** 一次性轻戳 → `send.sh` + 退出码。需要确知落地 → 信箱 + ack,用 ack 或副作用判成功,绝不用屏幕判。

## 模式二:旁路审计者(验证过的配方)

让会话 A 持续审计会话 B,而不碰 B 的仓库。

1. **定时**:用 `/loop`(如 `/loop 5m …`);cron 是会话级的。挑避开 `:00 / :30` 的分钟(如 `2-59/5 * * * *`),避开整点拥堵。
2. **派活前记录每个仓库的基线 HEAD**,后续每轮只审 `baseline..HEAD` 的新提交。
3. **只读审计**:对比上次记录的 HEAD → 有新 commit / spec / 未提交变更就读 diff + 代码,挑*落空的需求 / 自相矛盾 / 未验证假设 / 重复造轮子 / 盲点*。
4. **在你自己这边留底**——绝不写 B 的仓库,否则污染它的 `git status`。维护一个滚动的待办表。
5. **用 `git log` HEAD 变化当"完成"信号**,别用 `read-screen`:
   ```bash
   git -C "$($S/sessions.sh --repo demo-backend)" log --oneline -1
   ```
   HEAD 移动 = 它跑完了一轮。比盯 spinner 可靠得多。
6. **提防中间态**:对*正在活跃执行*的会话,单次 git 快照可能逮到"任务已提交、修复未提交"——别急着断言"未采纳",看提交趋势,或等它这轮结束。
7. **确认后再推给用户**——带 `file:line` + 精确修复建议,采纳率最高。
8. **brief 用文件派,不用聊天**:每个会话的任务 brief 写成文件,发一行指针。长 brief 贴进输入框会 wrap、半提交。

## 模式三:扇出与线程管理

一条回复常常要转给第三方(后端定稿接口 → 前端要知道)。多会话协作会迅速退化成"谁在等谁的什么"记不清。

- **用注册表分组批量定位**:
  ```bash
  $S/sessions.sh --group demo-project --status
  ```
  只给 `idle` 的发,`busy` 的排进下一轮。
- **维护一个线程文件**(你自己这边),每行一条:`<时间> <from> → <to> <主题> <状态:待回复/已闭环>`。这是你跨 tick 的记忆,别指望上下文。
- **广播要克制**:同一条消息发给 N 个会话 = N 次不可逆打扰。除非用户明确要求,否则只发给真正需要的那个。
- **给消息标注意图**:`[需回复]` / `[FYI]`,让对方知道要不要占用一轮去回。

## 模式四:组看板——把「共识」从消息流里救出来

文件信箱解决的是**投递可靠性**;组看板解决的是**共识留存**。三个以上会话协作时,
如果没有共享看板,协调者实际扮演「总线 + 记忆」:后端报进展 → 协调者核实 → 转前端;
前端发现契约缺口 → 报协调者 → 判断 → 转后端;而对话里达成的决策只活在
cmux 消息和提交信息里——一次实战协作结束后,不得不手工把 10 条实现期决策
(校验分级、选型、角色限制、id 序列化口径……)补进设计文档。

`board.sh` 维护 `~/.claude/cmux-messaging/boards/<组>.md`,固定三张表:

- **在做什么**:会话 / 当前任务 / 状态 / 阻塞于——组内忙闲的全局视图;
- **待决**:编号 / 问题 / 谁来定 / 提出时间——悬而未决的问题不再靠脑子记;
- **已定**:编号 / 决策 / 理由 / 时间——**决策的唯一真相源**。

用法约定:

1. **各会话直接读写同一份文件**(同机共享文件系统),写完按一声门铃:
   `group.sh <组> '看板已更新: <一句话>'`。消息只当门铃,内容以看板为准。
2. **凡在对话里定下的口径,当场 `--decide` 进看板**。判据:半年后有人翻旧账,
   两份互相矛盾的口径哪份算数?看板「已定」栏算数。
3. **接活/换任务/被阻塞时顺手 `--set-status`**,协调者就不用轮询每个人的屏幕。
4. 协调者醒来三连:`board.sh <组>` → `pending.sh list --group <组>` →
   `group.sh <组> --status`。看板(共识)、台账(欠账)、忙闲(现状)各看一眼,
   全局视图齐了。

## 协作约定:接活的会话不要「报告完就停」

实战反复出现:执行会话在报告末尾写「接着做第 2 块」,然后回合就结束了,
一直 idle 到协调者发消息推它——一轮协作里协调者推了五次以上。约定:

**接受派活的会话,做完一项后直接做下一项,不停下等确认**。只有四类事项必须
停下来报告并等回复:

1. **要改数据结构**(表结构、接口契约、共享模型);
2. **要推翻已定决策**(看板「已定」栏里的东西);
3. **环境不通**(依赖装不上、服务起不来、权限不足);
4. **要扩范围**(发现了 brief 之外该做的事)。

这四类之外的一切,做完 → 更新看板状态 → 继续。派活的 brief 里把这条约定写进去。

## 协作约定:验收角色要「独立复跑」,不要「采信报告」

审计/验收会话的最小动作集,每一条都验证过能拦住真问题:

- **自己重跑构建与测试**(`mvn test` / `pnpm build`),不采信对方的「已通过」;
- **读源码核约束,不读报告核约束**——报告是对方对自己工作的转述,转述会漂移;
- **对自己的判断同样接受反驳**:验收方也会犯错(把「不该存储」滑成「不该返回」、
  引用已被归档的选型当标准答案)。**双向可证伪**是这套协作真正有效的原因;
- 结论落盘:确认的问题带 `file:line` 进对方的待办,达成的口径 `--decide` 进看板。

## 反模式

- **把终端当消息队列** —— 它不是。要保证就上文件信箱。
- **无限等待回复** —— 永远设轮次上限,超了升级给用户。
- **往忙碌目标猛发** —— 会排队或卡箱,越发越糟。
- **审计笔记写进被审计者的仓库** —— 污染它的工作区,还会让它以为是自己写的。
- **靠屏幕判断"对方做完了"** —— 用 git HEAD / 文件产出 / ack 文件。
